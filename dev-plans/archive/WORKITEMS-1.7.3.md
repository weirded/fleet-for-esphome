# Work Items — 1.7.3

Theme: **ESPHome 2026.7 fallout + a dependency sweep.** A patch fast-follow to 1.7.2, cut ahead of the 1.8 LLM release because two of its fixes are the kind users can't work around. ESPHome 2026.7 replaced PlatformIO with a native ESP-IDF toolchain for ESP32; 1.7.2 fixed *installing* (#240) and *compiling* (#241) under it, and this release closes the remaining two holes that migration left — a shared-cache install race that could poison a multi-slot build worker permanently (#242), and factory-image downloads looking for firmware in the directory the old toolchain used (#244). Alongside those, fourteen merged Dependabot updates and two build-infrastructure fixes that were silently degrading the release gates themselves.

**A note on the `-dev.N` tags below.** This work was built and tested on `develop` while it carried the `1.8.0-dev.N` placeholder that `2848866` set when the 1.8 cycle opened. The release was renumbered to 1.7.3 at cut time — it is a patch by semver (bug fixes and dependencies, no new user-facing features) and `WORKITEMS-1.8.md`'s LLM-assistance scope is untouched and unstarted. The tags are left as the versions that were actually built, deployed, and smoke-tested rather than rewritten to a `1.7.3-dev.N` series that never existed.

## ESPHome 2026.7 toolchain fallout

- [x] **#242** *(1.8.0-dev.2)* — **Shared ESP-IDF cache install race poisons a worker permanently.** ESPHome installs the ESP-IDF framework + toolchain into a process-global cache (`platformdirs.user_cache_dir("esphome")/idf`) and does **no locking** around that install — verified: zero lock primitives in `esphome/espidf/framework.py`. We run `MAX_PARALLEL_JOBS` esphome processes concurrently against that one cache, isolating `PLATFORMIO_CORE_DIR` per slot (`client.py:1546`) and locking per-target build dirs (`_target_cache_lock`) but nothing for the IDF cache. **Live repro:** 2026-07-21, ESPHome 2026.7.1 bumped the required IDF 5.5.4 → 5.5.5; ai-macbook's two slots invoked 2026.7.1 in the *same millisecond* (`18:30:45.108` both) against a cold cache and raced the install, leaving `frameworks/5.5.5/` with **19,159 of 27,275 files and no `tools/` directory at all**. ESPHome checks only that the directory exists, fails validation, and raises `RuntimeError: ESP-IDF 5.5.5 framework installation failure` in ~0.5 s on every subsequent job — it never removes the partial tree to retry, so the worker is poisoned permanently. docker-optiplex-5 hit the toolchain flavour instead (`Dynconfig for target esp32s3 is not exist`). Net: 18 of 22 recent jobs failed, **only** on the multi-slot workers (ai-macbook 13, docker-optiplex-5 5) — single-slot `local-worker` and `OPTIPLEX-7` were clean on the *same* 2026.7.1. **Reinstalling the container made it worse, not better:** the IDF cache lives in the container's writable layer (only `/esphome-versions` is a volume), so every recreate guarantees a cold cache and simply re-runs the race. **Fix** (two halves, mirroring the #214/#220 PlatformIO precedent): (1) *prevention* — `_idf_install_lock` serialises the **first** compile per ESPHome version behind an exclusive `fcntl` lock so exactly one process performs the cold install; once warm, compiles take a shared lock and run fully parallel again, so steady-state throughput is unchanged. The warm marker lives **inside the IDF cache** (not on the persistent volume) so it dies with the thing it describes — a marker on the volume would survive a container recreate and wrongly report a fresh cold cache as warm, reintroducing the bug. `_idf_cache_looks_populated` gates the marker on `frameworks/<v>/tools` existing, so a compile that fails *before* ESPHome touches the cache (bad YAML, missing secret) can't false-positive it warm. (2) *self-heal* — `_is_broken_idf_state` matches the three observed signatures (`framework installation failure`, `Dynconfig for target … is not exist`, `cannot find -lnosys`) and `_wipe_broken_idf_cache` removes `frameworks/` + `tools/` and every warm marker, then retries once; the wipe re-acquires the lock **exclusively** because the cache is shared and wiping it under a live compile in another slot would break that slot. Carries the #219 disk guard (≥ 5 GiB free) so a wipe can't be followed by an ENOSPC re-corruption loop. Regression net `tests/test_idf_cache_race.py` (17 tests) — the core `test_exclusive_lock_blocks_a_second_slot` spawns two real processes (not threads: `fcntl.flock` is per-open-file-description) and **fails pre-fix at 0.0003 s vs the 1.0 s hold**. `.py`-only change, so it reaches already-deployed workers via the existing source auto-update without an image bump.

- [x] **#244** *(1.8.0-dev.3)* — *Factory-image downloads failed for ESP32 targets on ESPHome 2026.7's native ESP-IDF layout.* The compile succeeded and the firmware was written, but `_collect_firmware_variants` only knew PlatformIO's `.esphome/build/<device>/.pioenvs/<device>/` shape. ESPHome 2026.7 replaced PlatformIO with a native ESP-IDF toolchain for ESP32 and drops the `.pioenvs/<device>/` staging dir entirely, writing straight into `.esphome/build/<device>/build/` — so archiving found nothing and the build log ended in `no firmware binary was found under .pioenvs/`. Only the download/archive path was affected; plain OTA upgrades tolerate an archive miss. ESP8266 / LibreTiny are unaffected (still PlatformIO). **Fix:** probe both roots, first match wins, and reword the failure message which named `.pioenvs/` and so pointed at the wrong directory once ESP-IDF was in play. Regression net: two layout tests in `tests/test_client.py` plus an end-to-end `download_only` case in `tests/test_e2e_client.py`. Third piece of the 2026.7 toolchain migration after #240 (install) and #241 (compile). Community contribution — PR #232 (vposloncec).

**Live confirmation of #242, 2026-07-28.** A manual bulk upgrade of the hass-4 fleet — **65 devices to ESPHome 2026.7.3**, a version none of the workers had ever built — ran across all six workers simultaneously, three of them multi-slot (ai-mac, docker-optiplex-5, docker-pve at 2 slots each). Every slot hit a *cold* ESP-IDF cache for 2026.7.3 at the same moment: precisely the race that poisoned ai-macbook and docker-optiplex-5 on 2026.7.1 and took 18 of 22 jobs down with it. Result this time: **67 of 67 jobs succeeded, zero failures, zero poisoned workers.** The serialised cold install did its job and the fleet stayed up. This wasn't a staged test — it was the maintainer upgrading a real house — which makes it better evidence than the regression suite.

## Build & release infrastructure

Both of these were degrading the gates that decide whether a release is shippable — one turning `develop` red without a code change, the other turning a deploy target green when nothing had deployed. Neither ships in the product; both are in scope for a release whose job is to be trustworthy.

- [x] **#245** *(1.8.0-dev.4)* — *Unpinned lint tools turned `develop` red without a code change.* `.github/workflows/ci.yml` installed `ruff` and `mypy` unpinned, so the lint gate's verdict tracked whatever was newest on PyPI the moment a job ran. Ruff **0.16.0** landed between 2026-07-21 (last green run, ruff 0.15.22) and 2026-07-27 and widened its default rule selection: **754 findings on unmodified `develop`**, all stylistic defaults (`Optional[X]` → `X | None` (UP045), `BLE001` blind-except, `S110` try-except-pass), none a real defect. Confirmed pre-existing rather than sweep-induced by running ruff 0.16.0 against the pre-merge tree — 754 there vs 758 after (the 4 extra are the new `#242` ESP-IDF lock code, same stylistic classes). Also explains the stale `lint: FAILURE` on the three most recently-opened Dependabot PRs (#233/#234/#235) while older ones stayed green — their checks simply ran after 0.16.0 shipped. **Fix:** pin `ruff==0.15.22` + `mypy==2.3.0` in the lint job with a comment explaining why. Verified 0.15.22 is clean on post-sweep `develop`.

- [x] **#246** *(1.8.0-dev.5)* — *`haos-pve` deploys silently landed in a directory Supervisor stopped reading.* `scripts/haos/install-addon.sh` hardcoded `GUEST_TARGET=/mnt/data/supervisor/addons/local/<slug>`, but Supervisor moved its local add-on dir to `apps/local` (the same rename the script's own CLI verbs already follow — it calls `ha apps info` / `ha apps update`). **The failure is silent and total:** the tar lands, the extract succeeds, every log line reads healthy, and Supervisor never sees any of it. Verified on VM 106 — `addons/local/.../config.yaml` written today at `1.8.0-dev.3`, while the live `apps/local/.../config.yaml` still read `1.7.2-dev.8` with an mtime of **June 1**; every haos-pve deploy since then had been a no-op. The symptom surfaces two steps downstream as *"Timed out waiting for add-on to come up with v1.8.0-dev.3 (last seen: '1.7.2-dev.8')"*, which reads as a stale **image** and sends the reader to GHCR instead of to the deploy that never arrived — this is the infra half of **#243**'s *"audit why `test-matrix --from-ghcr` served a stale tag"* follow-up, and the reason its live repro saw a months-old container. **Fix:** probe for the real base on the guest rather than hardcoding, mirroring the identical probe `push-to-hass-4.sh` already carries — the base that *already holds* the add-on is by definition the one Supervisor reads; fresh installs fall back to the first existing base, newest layout first, and an empty probe is a hard error instead of a silent wrong-path write. Resolution moved after `guest_exec` is defined, so `GUEST_TARGET` is now bound at use rather than at declaration. Verified: haos-pve went from pinned-at-1.7.2-dev.8 to reporting `1.8.0-dev.4` on the next run.
