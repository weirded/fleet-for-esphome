# Work Items — 1.8

Theme: **LLM assistance.** A multi-provider LLM layer powering three use cases: an in-editor YAML assistant for the device a user is currently looking at, a fleet-wide chat that can read and modify configs across the whole fleet via tool calling, and a release breaking-change analyzer that scores ESPHome upgrades against the components each managed device actually uses.

Direction informed by a design conversation distilled into the items below — key decisions:

- **Multi-provider, not Anthropic-first.** Users will run Anthropic, OpenAI, Google, **plus local Ollama and LM Studio**. Use [`litellm`](https://github.com/BerriAI/litellm) as the single call surface — same code path for cloud and local; provider/model/api_base swap at call time, not init time.
- **No LangChain.** Heavy, breaking-change-prone, buys nothing for these use cases. The whole stack is `litellm` + `instructor` (for Pydantic-backed structured outputs) + the SDKs we already ship. Reference Python implementations to study (not embed): Aider (`aider-chat`) for the edit/confirm/apply loop; Anthropic's open-source `claude-code-sdk` for the agentic primitives.
- **Live-reload, not restart.** LLM settings live alongside everything else under SP.* (1.6's Settings drawer). Because LiteLLM takes credentials per call, a settings save takes effect on the next request — no add-on restart.
- **Permission tiers, not "just YOLO".** Three modes — `READ_ONLY` / `SUGGEST` (stages a diff for user approval) / `AUTO_APPROVE` (writes directly). Default `SUGGEST`; `AUTO_APPROVE` is opt-in per provider.
- **Tool calling, not context stuffing.** For fleet-wide questions, give the model a small set of tools (`list_devices`, `get_device_config`, `search_configs`, `stage_device_change`) and let it pull what it needs. Users with 20+ devices would otherwise blow the context window every prompt.
- **Stage, never write directly.** Every write tool stages a diff into a pending-changes panel; user approves before anything touches the filesystem. Same pattern Aider and Claude Code use.

## Foundation: LLM provider layer

- [ ] **LL.1 LiteLLM call surface** — single `llm_call(messages, *, structured_model=None, tools=None, stream=False)` wrapper around `litellm.completion`. Reads provider/model/api_key/api_base/temperature/max_tokens from the live settings object on every call (no client init at startup). Models named in `<provider>/<model>` form (`anthropic/claude-opus-4-5`, `openai/gpt-4o`, `ollama/llama3.2`, `openai/local-model` for LM Studio with `api_base`). New dep: `litellm` in `requirements.txt` + lockfile (PY-8).
- [ ] **LL.2 Settings drawer "AI" tab** — extends the SP.8 settings store. Fields: `enabled` (bool), `provider` (dropdown: anthropic / openai / google / ollama / lmstudio), `model` (free-text — model lists rot, let users type what they actually have), `api_key` (secret, hidden for local providers), `api_base` (only shown for ollama/lmstudio), `temperature` (slider, default 0.2 — YAML edits want determinism), `max_tokens` (default 4096), `permission_mode` (`READ_ONLY` / `SUGGEST` / `AUTO_APPROVE`, default `SUGGEST`). Conditional show/hide on `provider`. Persists to `/data/settings.json`. Live-reload via the existing SP.8 broadcast.
- [ ] **LL.3 "Test connection" button** — beside the AI fields. Sends a 10-token "reply with OK" prompt through the configured provider and surfaces success / latency / error inline. Catches the most common config mistakes (wrong key, wrong api_base, model name typo) before the user discovers them mid-edit.
- [ ] **LL.4 Permission tier enforcement** — every write tool checks `settings.ai.permission_mode` before acting. `READ_ONLY` rejects writes with a clear "permission denied" tool result. `SUGGEST` stages the change to an in-memory pending-changes map keyed by `(conversation_id, device_name)` and returns `{"status": "staged"}`. `AUTO_APPROVE` writes directly. Tier shown as a badge in the chat UI so users can see what's active.
- [ ] **LL.5 Structured streaming events** — internal pydantic event model `AgentEvent { type: "thinking" | "tool_call" | "tool_result" | "text" | "diff" | "error", content: str | dict, ts: float }`. The agent loop yields these; `/ui/api/ai/stream` surfaces them over WebSocket so the chat UI can render thinking indicators, tool-call badges, and inline diffs progressively rather than waiting for the full turn.
- [ ] **LL.6 Conversation persistence** — full message history (text + tool_calls + tool_results) persisted to a small SQLite table alongside JH.* (1.6's job history DB), keyed by `conversation_id`. Survives add-on restart, lets the model say "as we discussed earlier when I read your porch sensor config…" Retention bound: keep last N=20 conversations, prune older.
- [ ] **LL.7 Hardcoded "weak local model" warning** — when `provider in {ollama, lmstudio}` and the model string doesn't match a known-good list (Llama 3.1+, Qwen 2.5+, Mistral Large), show a one-line warning under the model field: "Tool calling may be unreliable on this model — recommended: …". Doesn't block, just sets expectations. Worth doing because tool-calling failures on small local models are confusing — the model "answers" without ever calling the tool that would have given the right answer.
- [ ] **LL.8 No telemetry / no cloud egress when disabled** — when `ai.enabled = false` we make zero outbound LLM calls and the AI tab in the editor is hidden. Spot-check with `tcpdump`/integration test. Pat-friendly: a user who never turns AI on never sees a cent of cloud cost or a packet leaving their network.

## Per-device YAML assistant (in-editor)

The editor (Monaco-based, already shipped) gains an AI sidebar for the device the user is currently editing. Per-device, single-file scope — the global fleet chat (FC.*) handles cross-device prompts.

- [ ] **AI.1 `POST /ui/api/ai/complete`** — completion endpoint scoped to one file. Body: `{device_name, yaml_content, cursor_offset, prompt}`. Returns the completion stream. Used by AI.3's inline ghost text and AI.4's chat panel. Uses `instructor` + the `ESPHomeEdit` Pydantic model below for the diff path; raw streamed text for free-form completions.
- [ ] **AI.2 `ESPHomeEdit` Pydantic model** — `class ESPHomeEdit(BaseModel): modified_yaml: str; explanation: str; warnings: list[str]`. Wraps every "modify YAML" call so the LLM has to return parseable structured output rather than freeform text we'd have to fence-strip. Fallback: if `instructor` parse fails (older / smaller models), regex-extract the first ` ```yaml ` block and surface a warning event.
- [ ] **AI.3 Inline ghost-text completions** — Monaco inline-completion provider that calls AI.1 on idle (debounced ~500 ms after typing stops). Shows the suggestion as ghost text; Tab accepts, Esc rejects. `permission_mode` does not gate this — it's user-initiated and user-applied keystrokes, no filesystem write happens until they save the file the normal way.
- [ ] **AI.4 Chat side panel in editor** — collapsible panel beside the Monaco view. Free-form prompt → response is either an `ESPHomeEdit` (rendered as a Monaco diff with Accept / Reject buttons) or freeform text (rendered as markdown). On Accept under `SUGGEST` mode, applies the change to the editor buffer (still requires the user to hit Save — symmetric with manual edits). On Accept under `AUTO_APPROVE`, saves automatically.
- [ ] **AI.5 ESPHome-aware system prompt** — module-level constant containing: "You modify ESPHome YAML configs. Output must be valid YAML. Preserve `# distributed-esphome:` comment blocks verbatim. Prefer existing substitutions / packages / secrets over inlining values. Never embed real WiFi passwords or API keys — use `!secret` references." Versioned (`ESPHOME_PROMPT_V = 1`) so we can iterate without surprising users with regressions.
- [ ] **AI.6 Diff-only reject path** — when the user rejects a staged AI.4 diff, we don't just discard — we feed the rejection back into the conversation as `"User rejected this change"` so a follow-up "try again" prompt has the context. Cheap to implement, big UX win.

## Fleet chat (global)

A new top-level **AI Assistant** tab. Free-form prompts against the whole fleet, powered by tool calling so we don't blow the context window stuffing every YAML upfront. Where the per-device AI panel knows about one file, this knows about everything.

- [ ] **FC.1 Agentic tool loop** — the canonical "while tool_calls is not None" loop on top of LL.1. Yields LL.5's `AgentEvent`s as it goes (thinking → tool_call → tool_result → text). Loop bound: max 25 tool calls per turn (defensive — a runaway agent can easily eat thousands of tokens; surface "I hit the tool-call limit" to the user rather than silently truncating).
- [ ] **FC.2 `list_devices` tool** — returns `[{name, board, platform, components: [...], tags: {...}}]` for every device in the fleet. Reuses `scanner.py`'s parsed config — no re-parsing per call. Cheap (~one row per device), so it's the LLM's first move on most prompts.
- [ ] **FC.3 `get_device_config` tool** — reads one device's full YAML. Bounded by `safe_resolve` (`ha-addon/server/helpers.py`) so the LLM cannot escape `/config/esphome/`. Returns `{yaml: str, sha: str}` so a later `stage_device_change` can detect drift between read and write.
- [ ] **FC.4 `search_configs` tool** — substring + regex search across all YAMLs. Returns `[{device, line, snippet}]`. Cheap way for the model to answer "which devices use the deprecated `xyz` component?" without reading each config in full.
- [ ] **FC.5 `stage_device_change` tool** — write-equivalent. Takes `{device_name, modified_yaml, reason, expected_sha?}`. Under `SUGGEST` mode (default), inserts into the pending-changes panel and returns `{"status": "staged", "id": "..."}`. Under `AUTO_APPROVE`, writes via the existing AV.* commit path so changes flow through git history. Refuses if `expected_sha` doesn't match the current file (concurrent-edit guard — important if the user is editing the same device in the editor at the same time).
- [ ] **FC.6 `read_release_notes` tool** — wraps BC.1's release-notes fetcher so the chat can answer "what changed in 2026.5.0?" without us pre-emptively passing it. Pairs with the breaking-change analyzer — users will naturally ask about a release in chat after seeing the BC.* impact report.
- [ ] **FC.7 Chat UI** — new tab with: conversation list (left), active conversation (center, streaming `AgentEvent`s), pending-changes panel (right, shows staged diffs with Accept-all / Reject-all / per-row controls). Permission badge in the header. "New conversation" button. The pending-changes panel is the single place users review every staged write before it lands — same pattern as the per-device AI.4 diff but aggregated across the conversation.
- [ ] **FC.8 Bulk-apply staged changes** — Accept-all on the pending-changes panel commits all staged writes in one batch via `Promise.all`, surfaces a single summary toast (per the "Batch operations get one toast" design judgment in CLAUDE.md). Each write goes through AV.*'s git path so the auto-commit subject reflects "AI: <reason from FC.5>" rather than a generic message.
- [ ] **FC.9 Conversation history view** — left rail lists prior conversations from LL.6's persistence. Click to resume — the model picks up where it left off, including tool-call results. Pruning: oldest dropped when over the 20-conversation cap.
- [ ] **FC.10 Cost / token surface** — small footer in the chat tab showing tokens used this turn + cumulative for this conversation, plus a per-provider $/1K-tok hint where known. Local providers show "$0.00 (local)". Optional but high-value for users on metered plans — the conversation can otherwise hide its real cost.

## ESPHome release breaking-change analyzer

Largely as scoped before — adapted to ride on LL.* (LiteLLM, structured outputs). Naturally paired with FC.6 so the chat can drill in after the upfront report.

- [ ] **BC.1 Release notes fetcher** — pull ESPHome release notes from the GitHub releases API (fallback: `esphome.io/changelog/`); cache under `/data/esphome_releases/<version>.json`. No GitHub auth required for public repos; rate-limit is generous and we cache.
- [ ] **BC.2 Device component inventory** — for each managed device, extract the set of components / platforms in use from its parsed YAML. Reuse `scanner.py` parsing — do not hand-roll regex per PY-1.
- [ ] **BC.3 `POST /ui/api/ai/analyze-release`** — input: `{target_version, device_filter?}`. Calls LL.1 with an `instructor` model `BreakingChangeReport { items: list[DeviceImpact] }` where `DeviceImpact = { device, risk: "none" | "low" | "high", affected_components: list[str], summary: str, links: list[str] }`. The "links" are anchors into the cached release notes so the UI can deep-link.
- [ ] **BC.4 UI entry points** — "Check breaking changes" action on the ESPHome version picker and on the Upgrade Outdated flow. Results modal grouped by device (high → low → none), with expandable per-component detail and a "Discuss in chat" button that opens a fresh FC.7 conversation seeded with this device's report.
- [ ] **BC.5 Result caching** — key by `(release_version, device_yaml_sha256)`. Re-opening the modal is instant; LLM calls only happen when something actually changed (release version bumps, or the device's YAML edits). Stored alongside BC.1's release notes cache.
- [ ] **BC.6 Surface in HA Updates** — paired with the future `UE.*` work in `WORKITEMS-future.md`, expose the `risk` value on the per-device update entity's `release_summary` so HA's native update card shows "⚠ 2 high-risk components affected" without the user having to open the Fleet UI. Stretch — drop if `UE.*` isn't on the table for this release.

- [x] **PR #252 / [#195](https://github.com/weirded/fleet-for-esphome/issues/195) / [#110](https://github.com/weirded/fleet-for-esphome/issues/110)** *(1.8.0-dev.7)* — *A worker that compiles fine but cannot reach the device now hands the OTA to the add-on instead of failing the job.* Extends #133's Thread/Matter mechanism to ordinary WiFi/Ethernet devices. Where #133 routes OTA through the add-on for targets *statically* known to be unreachable from any worker (Thread's IPv6 mesh), this covers the case that is only knowable at runtime: *this* worker cannot reach *this* device — a VLAN split, a firewall, a cloud worker with no tunnel home. Before `esphome run`, the worker TCP-probes the device's OTA port; if nothing answers it compiles, archives the binary, and sets `requires_server_ota`, and the server reuses #133's `_server_ota_push` unchanged — same badge, same history column, same code path. A second trigger covers what a TCP probe structurally cannot see: a device that accepts the connection and then fails the OTA protocol exchange (a lossy RF link — the live case was `Connected to …` followed by `ERROR receiving update prepare result response: timed out` with 100 % ping loss), so a local OTA failure that survives the existing retry also hands off, gated on the firmware having archived successfully. **Behaviour change worth stating plainly:** this is **on by default and affects every WiFi/Ethernet upgrade**, not only Thread ones. A false negative costs one extra add-on-side attempt; the upside is that a genuinely unreachable device produces a finished upgrade rather than a failed job. Known false-negative cases are documented in `DOCS.md` (deep-sleep devices not listening between wakeups, firewalls that drop SYN rather than refusing, an OTA port set via a `${substitution}` which the literal scan can't resolve — that one falls back to probing both 3232 and 8266). `OTA_REACHABILITY_CHECK=0` disables both triggers and is documented in the add-on panel, not just contributor docs, because it is the user-facing escape hatch. **Two production bugs the contributor found and fixed while running this live:** the OTA port scan matched the first `port:` anywhere after the substring `"ota:"`, so a later `web_server:` block could supply it (live repro probed `:80`); and `_server_ota_push`'s pre-flight ping hardcoded `ping6`, which was fine while the path was Thread-only but fails instantly with "Address family for hostname not supported" now that IPv4 devices reach it. **Review round (this release):** found a third case of the same port-detection bug class — the block-scoped rewrite fixed the file-scope version but not the one *inside* the block, so a multi-platform `ota:` list (legal since ESPHome 2024.6) returned whichever platform was written first; a `web_server` OTA platform on 8080 declared above the `esphome` one on 3232 answered `[8080]`, and probing a port nothing listens on yields a false "unreachable" and a pointless hand-off. Fixed with `findall` + `dict.fromkeys` (order preserved; the caller already loops and short-circuits on the first port that answers, so returning both is strictly better than choosing), pushed to `fix/ota-port-detection-multiplatform` and cherry-picked by the contributor as `76a252d`. Also raised: a bare `# noqa: PLC0415` with no reason (PY-5), and `_server_ota_push`'s generic `except Exception` not killing `proc`, letting an `esphome upload` outlive the temp dir holding the binary it is reading — both fixed in `bb1bf3e`, the latter with a regression test driving a `"RAISE"` sentinel through the existing `_FakeStdout` fixture. **PY-1 disposition:** the hand-rolled `ota:` block scan stays, and the `ALLOW_REGEX_YAML` comment now gives the real reason — `yaml.safe_load` has no constructor for `!secret` and raises on it *even where PyYAML is installed*, so "workers might lack PyYAML" alone would have invited someone to re-add the parse behind a `try/except ImportError` and re-break every config using a secret. **Verified on merge:** `protocol.py` copies byte-identical (PY-6), ruff clean, mypy client clean, invariants 18/18, **1144 passing (+17)** with zero non-socket regressions, and `_detect_ota_ports` confirmed returning `[8080, 3232]` on the multi-platform fixture in the merged tree.

- [x] **PR #133 / [#132](https://github.com/weirded/fleet-for-esphome/issues/132)** *(1.8.0-dev.5)* — *Server-side OTA for Thread/Matter devices: remote workers can compile for them but can never flash them.* Thread devices live on an IPv6 mesh reachable only from the host with the Thread radio — the HA box. A worker on another subnet compiles fine and then fails every upload, and no amount of tag-pinning fixes it for users whose only worker *is* remote. **Fix (contributed by @htilly):** split compile from flash. Any worker compiles and uploads the binary back (reusing the existing `download_only` plumbing), then the add-on performs the OTA itself with `esphome upload --device <addr> --file <bin> <target.yaml>`. Auto-detected at enqueue from `network_type == "thread"` in both `ui_api.start_compile` and the scheduler, so the user never picks it; the Queue tab renders the extra phase as `Compiling → Server OTA` (live upload %) `→ Success | OTA Failed`. **Design points worth keeping:** the timeout is *progress-based*, not a flat cap — Thread OTA legitimately takes minutes on a lossy mesh (observed: 900 KB in 195 s at 0.9–2.4 s RTT), so a total-duration bound kills transfers that are still working; the push reads the subprocess incrementally, resets a 90 s idle clock on every chunk, and keeps a 30-minute absolute backstop, with `--dashboard` passed so ESPHome's ProgressBar emits frames over a non-tty pipe to feed both the clock and the UI percentage. Factory images are refused outright — that variant is a full flash image at absolute offsets and pushing it through the OTA protocol writes the wrong bytes into the OTA partition — so only `ota` / the legacy `firmware` name is accepted. Restart recovery: the push is an in-process task that runs *after* the job is already SUCCESS, so neither the `WORKING → PENDING` reset nor `timeout_checker` would ever revisit it; `JobQueue.load()` now marks that shape `ota_result="failed"`, which is the honest outcome instead of a row spinning on "Server OTA" forever. **This is the first path that runs `esphome upload` on the HA host itself**, so: the push task is held in a module-level set (asyncio keeps only a weak reference and 30 minutes is a long time to be collectable), bundle extraction uses `filter="data"` matching the worker, and `ota_address` — which reaches `--device` and the pre-flight `ping` as argv — is now validated by the new `helpers.is_valid_ota_address` at the `/ui/api/compile` boundary. Nothing goes through a shell so there was no injection surface, but both consumers parse a leading dash as a *flag*, and the old validation was only "a string ≤253 chars". **Review verification:** the validator was exercised directly — rejects `-f`, `--device`, `--help`, `-192.168.1.1`, `1.2.3.4;rm -rf /` and bare `-`, accepts scoped IPv6 (`fe80::1%eth0`, which Thread needs). `protocol.py` copies byte-identical (PY-6); `server_ota` is additive + optional with a `False` default so old-worker↔new-server and new-worker↔old-server both degrade correctly, no `PROTOCOL_VERSION` bump. Gates on the merge result: ruff clean, mypy client clean (server unchanged — the one pre-existing `ui_api.py:1219` error), invariants 18/18, **+34 net passing tests**, and every new failure in this sandbox is the environmental `SocketBlockedError` class, byte-identical to the develop baseline. Merge conflict with develop was a single adjacency in `constants.py` — #239's `WORKER_DISK_FREE_FLOOR_BYTES` and this PR's OTA timeouts appended to the same spot; both kept. **Follow-up not blocking this merge:** `api._server_ota_push` schedules its `refresh_target` with a bare `create_task` inside the very function that introduced the strong-reference set — harmless (it mirrors the existing call at `api.py:900` and is short-lived) but inconsistent; and the inline `import socket` carries a bare `# noqa: PLC0415` with no reason, which PY-5 asks for.

- [x] **#114** *(1.8.0-dev.3)* — *Add-on fails to start with `OSError: [Errno 98] address already in use`, and the log makes it look like a stop request.* `main.py` called `web.run_app(app, host="0.0.0.0", port=cfg.port)` bare. aiohttp runs the registered `on_shutdown` handlers before re-raising the bind error, so the log reads *"Started local worker → Shutting down Fleet for ESPHome → APScheduler stopped → mDNS unregistered → DevicePoller stopped"* and only then the traceback — a clean shutdown sequence followed by an error, which every reader parses as "something SIGTERM'd it". The reporter went four comments deep before the `EADDRINUSE` line at the bottom got noticed, then a further round to find the cause: the **OpenThread Border Router** add-on, which also runs `host_network: true` and binds 8765, so whichever add-on starts first owns the port. **What makes it worse:** the add-on's Configuration tab has a port field, so the natural next move is to change it — and it does nothing. Under `host_network: true` Docker does no port mapping at all, and `ingress_port: 8765` (`config.yaml:45`) is read once by Supervisor at install time to set up the Ingress proxy; the server must bind exactly that port or the UI breaks. There is no Supervisor API for a dynamic `ingress_port`, so the port genuinely is not user-changeable — the field is cosmetic here. **Fix:** `run_server()` wraps `web.run_app`, catches `OSError` with `errno.EADDRINUSE`, and logs one critical line that names the likely conflicting add-on with the command to stop it, says the Configuration-tab port field will not help and why, and tells the reader the shutdown messages just above are cleanup rather than a stop request. Non-`EADDRINUSE` `OSError` re-raises unchanged. Message text lives in `bind_conflict_message(port)` so it is assertable. Plus a **Troubleshooting** section in `ha-addon/DOCS.md` — this is a first-five-minutes failure and the user cannot reach the in-app UI to read anything else. Deliberately *not* doing the long-term half the reporter also proposed (moving the default port off 8765): that is a breaking change for every external worker's `SERVER_URL` and belongs in a release that already carries a migration note.

- [x] **#199** *(1.8.0-dev.3)* — *Every per-target and per-worker entity goes `unavailable` after each HA restart or integration reload, showing "This entity is no longer being provided by the esphome_fleet integration."* `_discovery.entity_already_registered()` — added by PR #62 to stop `_discover()` double-adding — asked HA's **entity registry** whether a unique_id was known. That registry is persisted to disk; the `CoordinatorEntity` instances it points at are session-scoped, rebuilt by `async_setup_entry` and dropped on unload. So on the first coordinator tick after any restart the registry answered "yes, seen it" for *every* per-target and per-worker unique_id, `_discover()` skipped all of them, and the registry rows were left owned by nothing — which is exactly the state HA renders as `unavailable` + "no longer being provided". Cluster-level sensors were unaffected because they are added unconditionally rather than through `_discover()`, which is what made the report so precise about which entities died. **Fix:** ask the **live** `entity_platform.async_get_platforms(hass, DOMAIN)` map instead. It is rebuilt from scratch on every setup, so after a restart the answer is "no", `_discover()` re-adds, and HA reattaches the entities to their existing registry rows by unique_id — entity_ids, names, areas and history all preserved. Within a session the answer flips to "yes" as soon as an entity is live, so #62's duplicate adds stay fixed, and a removed entity leaves the live map too, so #62's *original* add/remove-cycle symptom is also still covered. Unique_ids are config-entry-scoped (`f"{entry_id}_target_…"`), so scanning every platform the integration owns cannot collide across entries. **Diagnosed and patched by the reporter**, who traced it through `_discovery.py` and ran the fix on their own box before filing — nearly every entity came back after a restart, with only genuinely-offline devices left unavailable. Regression net: `tests/test_integration_entity_discovery_logic.py`, 7 cases covering the restart path, the within-session dedupe, platform-domain matching, the add/remove cycle, and a guard asserting the module never re-imports `entity_registry` — the import *is* the bug, so the import is what the test watches.

- [x] **#171 / #197** *(1.8.0-dev.3)* — *Editing a device's static IP in the YAML never changes the address Fleet displays.* `DevicePoller.update_compile_targets()` runs on every config rescan and is where a YAML edit should land, but it applied the YAML-derived address only when the row had none (`if not dev.ip_address`). Any row that had ever been populated — by an earlier scan, or by mDNS — kept its first address for the life of the process. `resolve_ota_address()` reads the *override* map, which is rebuilt from the YAML on each scan, so after an edit the two disagreed: OTA flashed to the new address while the Devices tab kept showing the old one (#171's screenshot). The same split is behind #197's "wrong IP addresses are resolved for some devices" — mDNS unconditionally overwrote `dev.ip_address` with whatever it observed, even when the YAML pinned an IP literal that `resolve_ota_address` would use regardless (branch `override_ip_literal` outranks `dev.ip_address` unconditionally), leaving the UI permanently disagreeing with the address every upload targeted. **Fix, two halves, deliberately paired:** (1) `update_compile_targets` now updates an existing row when the YAML address differs *and* the source is an explicit user choice (`wifi_static_ip`, `*_use_address`, …), logging the old → new transition. (2) the mDNS handler no longer overwrites `dev.ip_address` when the YAML pins an IP literal that differs — it logs the disagreement once per device instead ("device answers at X but its YAML pins Y — keeping the YAML address, which is what OTA targets"). Fixing only (1) would have produced a flip-flop, with each rescan setting the YAML address and each mDNS announce setting it back. **Guard rail:** `mdns_default` — our own `{name}.local` guess, not a user choice — is excluded from (1), so a real mDNS-discovered IP is never displaced by the fallback hostname; that would undo bug #60. Note the *upload-failure* half of #171 was already fixed by #18/#134 (`resolve_ota_address`) and both reporters were on 1.7.1, before #134 shipped. 5 regression tests in `test_device_poller.py`; 3 fail against the old code, 2 are the guard rails and must keep passing.

## Notes & non-goals

- **One LLM call per user action.** No background "ambient" calls — no auto-summarising YAML on every save, no auto-tagging devices, no "AI nudges". Pat is paying per token; opt-in is the floor.
- **Filesystem boundary stays at `/config/esphome/`.** AI tools never touch `/config/` outside ESPHome, never reach into `/data/`, never see the worker registry token. Enforced by `safe_resolve` per the existing helper.
- **No fine-tuning, no RAG infrastructure.** The fleet is small enough that tool calling + targeted reads handles every realistic prompt. Embeddings + a vector store would be over-engineering for ~20 YAML files.
- **No agent autonomy across the WAN.** The agent loop only runs in response to a user prompt in the chat tab — no scheduled "review your fleet weekly" pings. If we add scheduling later (`AI Tasks API` style), it gates behind an additional opt-in.
- **Local-first viable.** Everything works with Ollama / LM Studio for users who refuse cloud LLMs entirely. Tool-calling reliability is the main caveat — LL.7's warning sets that expectation.
